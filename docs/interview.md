# FlashFlow interview explanation

## Five-minute walkthrough

**0:00–0:40 — Problem.** FlashFlow demonstrates an event-driven retail dashboard where inventory can change faster than React should render. The catalog has 500 deterministic products. The engineering problem is keeping both durable state correct and displayed data fresh during a surge. Smooth animation alone does not prove freshness: an earlier browser sample showed roughly 60 FPS while event-to-card P95 was 13.6 seconds.

**0:40–1:35 — Backend.** A single simulator produces versioned inventory events with `product_id` as the Kafka key. Kafka provides durable buffering, replay and per-partition ordering. Configurable consumer group members share one API/gateway process. Each member processes its assigned records in order. Inventory batches lock product rows in sorted order, preload receipt IDs, validate every stock transition and persist inventory, idempotency receipts and pricing audits in one PostgreSQL transaction. PostgreSQL is authoritative; Redis stores revision-guarded hot state and a separately refreshed fallback catalog.

**1:35–2:20 — Frontend.** The WebSocket gateway enqueues updates into bounded per-client queues, while independent sender tasks perform socket I/O. A slow client times out or disconnects without blocking other clients. The browser validates snapshots, buffers the latest product update and flushes once per animation frame. Zustand stores normalized products with product-specific subscriptions, and memoized cards avoid unrelated renders. Inventory and price revisions both have to move forward. Four modes make the difference observable: NAIVE, ATOMIC, MEMOIZED and BATCHED.

**2:20–3:20 — Bottleneck and optimization.** I instrumented source creation, producer enqueue/acknowledgement, broker append when available, consumer dispatch, SQL, pending-price publication, Redis, socket enqueue/send, browser queue and card commit. A timing-only serial reproduction attributed most service time to per-record database work, followed by pricing-publication queries and individual offset commits. Producer acknowledgements and socket fanout were much smaller in measured runs. I batched durable mutations and receipts, queried pending publications once per batch and committed only the last contiguous successful partition offset. Consumer-count comparisons separated batching from scaling. The raw before/after and sustained tables in [the report](throughput-report.md) show the improvement and the remaining high-rate backlog boundary.

**3:20–4:10 — Reliability and pricing.** Kafka delivery is at least once. A crash after SQL commit but before offset commit can replay a batch; receipt and decision IDs prevent double inventory or price effects, and replay repairs Redis/socket delivery. Bad records require acknowledged DLQ publication. Infrastructure failures retain offsets. A catalog-read circuit breaker opens after failures, serves a validated Redis snapshot with stale age, admits a half-open probe after its timeout and restores LIVE on success. Pricing is an explainable rule engine with stock/demand signals, cent-level bounds, cooldown/reversal protection and a durable outbox; there is no trained ML model.

**4:10–5:00 — Evidence and limits.** I compared one, two and three actual Kafka group members, ran a two-minute backend rate matrix, corrected a long-run receiver heartbeat flaw and repeated socket measurements, tested a five-minute 500/s soak, checked 1/10/50/100 real clients and revalidated all rendering modes. I distinguish configured rates from actual production/completion rates and socket receipt from rendered latency. High-rate runs accumulated backlog despite zero processing failures: this machine's local results are not production capacity guarantees. Gateway scale would require shared fanout, managed data services, TLS/auth, distributed tracing and group-wide telemetry. Normal CI, integration and heavy benchmarks have separate workflows; remote CI remains unverified until publication.

## Fifteen questions and answers

1. **Why Kafka?** It provides durable buffering and replayable offsets, decouples production from processing, preserves partition order and distributes partitions across a consumer group. It does not make PostgreSQL, Redis and browsers one atomic transaction.
2. **Why the product ID key?** Updates for the same product stay in the same partition within a topic. Different products can use different partitions. Changing the partition count changes key mapping, so existing topics need a controlled migration. There is no total ordering across inventory and pricing topics.
3. **Why not Redis Pub/Sub alone?** Pub/Sub is useful for future gateway fanout but has no durable replay for offline consumers. Kafka retains authoritative events; PostgreSQL stores durable business effects. Browser snapshot repair remains necessary even with shared Pub/Sub.
4. **What caused the lag?** The historical sample establishes consumer backlog but lacks stage traces. A measured serial reproduction showed database work dominating service time, with extra pending-price queries and individual offset commits. A matched short batched run sharply reduced lag and socket latency. The report gives raw totals and scope limitations rather than pretending to reconstruct unrecorded historical stages.
5. **How did consumer groups help?** Actual group members split the six inventory and six pricing partitions. The 500/s comparison measured lower socket P95 with two and three members than with one. All members are co-located to share the gateway; this is not a measured multi-host deployment.
6. **How is ordering preserved?** Each member processes partition records sequentially; batches apply those records in order. Sorted PostgreSQL row locks, strict next-version validation and separate price revisions protect cross-topic concurrency. Invalid version gaps are not silently accepted.
7. **How do you avoid duplicate inventory updates?** Receipt IDs commit with stock mutations. Under the row lock, an existing receipt returns a duplicate outcome. Batches preload receipts and track new IDs within the transaction. A rollback leaves neither mutation nor receipt; redelivery can safely retry.
8. **Why PostgreSQL plus Redis?** PostgreSQL supplies transactional inventory, receipts and auditable decisions. Redis supplies hot state and a validated full-catalog fallback. Cache revision guards prevent older cross-topic snapshots overwriting newer entries. Stale Redis state never becomes authoritative stock.
9. **How does the circuit breaker work?** Consecutive catalog-read failures open it. During the recovery timeout reads use cached fallback. A serialized half-open read probes recovery; success closes the breaker and failure reopens it. Circuit/fault state is process-local, and consumer retries are separate from catalog-read circuit behavior.
10. **How does rAF micro-batching work?** Network callbacks validate incoming updates and keep the newest accepted product snapshot in a map. One scheduled animation frame drains the map into a single store mutation. Multiple hot-product events can collapse into one rendered state without dropping durable backend events.
11. **Why Zustand?** Product selectors subscribe to normalized state without wiring a global array through every card. Updates keep unrelated object identities, so only relevant subscriptions change. Memoization handles parent-driven work; it is different from network batching.
12. **What happens to a slow WebSocket client?** Its queue is bounded. Queue overflow disconnects it with 1013, and send timeouts remove stalled senders. Other clients have independent queues/tasks. Reconnect fetches durable state; socket delivery is best-effort and is not an inventory acknowledgement.
13. **How would WebSocket servers scale?** Separate durable consumers from gateways and publish processed snapshots through shared Redis/broker fanout. Gateways retain bounded local queues and snapshot repair. Use WebSocket-aware TLS load balancing and graceful drain. Merely adding API worker processes would strand clients on partial group traffic.
14. **Is the system exactly once?** Kafka delivery is at least once with manual grouped commits. Database effects are effectively once per receipt/decision ID. Cache writes and socket messages can repeat. No Kafka transactional exactly-once claim is made.
15. **What would you change for production?** Add authentication/authorization, TLS, connection/request limits, managed Kafka/PostgreSQL/Redis, deployment-job migrations, backups/restore, retention for the growing receipt/audit tables, schema compatibility and distributed tracing/Prometheus. Run isolated multi-host tests and rebalance/failure drills before setting an operating envelope. Kubernetes is not required to demonstrate the current design.
