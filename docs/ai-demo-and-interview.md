# FlashFlow retail demo and interview guide

## A three-to-five-minute demo

1. Open Operations at `http://localhost:3000`. Explain that stock changes are simulated, forecasting is advisory, and one real minute represents one simulated hour. Allow approximately one real minute for cold-start feature history; unavailable data is shown explicitly.
2. Choose **Studio headphones** or another dedicated Retail Demo product. Its starting stock and previous operator actions affect the outcome; do not promise a particular stock count. Select Normal Demand for a brief baseline, or use the existing collected history. The polished Flash Sale lasts 36 ticks, roughly three real minutes: twelve normal warm-up bins then 24 ramped bins. Its explicit Kafka preparation tops up to eighty available units and never removes excess inventory. Other default scenarios last 24 ticks; one active scenario is allowed at a time.
3. Start Flash Sale. Point out attempted, fulfilled and stock-constrained counts. Open Products if the selected product has not yet reached Needs Attention. Stock and sales now change through Kafka, not browser mutation.
4. Inspect its details. Solid green charts show observed sales/stock/price; the blue dashed panel shows a future sales prediction band. Explain why the forecast can change, why it is stock-constrained, and why its range is uncertain.
5. As risk rises, inspect a pending replenishment recommendation. Read the human-readable inputs, then expand Calculation details for the unchanged quantity formula. Ask AI Analyst about the selected product; show tool names, timestamps and stored pricing evidence. It is labelled evidence-only and makes no external LLM call.
6. Approve one pending recommendation. If it expired during inspection, wait for materially changed or cooldown-eligible advice and use a fresh recommendation. The status becomes ACCEPTED while the outbox awaits processing, then EXECUTED after a durable receipt. Watch stock increase and the next forecast reassess risk. Rejection is also audited and does not mutate stock.
7. Show Recommendations/action history, then ask what happened during the flash sale. Distinguish fulfilled purchases from demand attempts.
8. Finish on Engineering: consumer lag, per-partition lag, database/Redis/socket stages, rendering modes and independent model health. Smooth FPS and low event age are different claims. Refer to recorded benchmark files rather than treating the configured rate as achieved throughput.

The verified bounded integration demo used twelve flash-sale ticks and exercised both rejection and approval, confirmed Kafka restock execution, completed the scenario and ran a separate restock. UI demos may use the default longer duration. To repeat after a depleted demo, use Restock when no scenario is active. There is no destructive reset button or hidden stock mutation.

## Five-minute technical explanation

**First minute — purpose and core.** FlashFlow turns simulated retail events into auditable operational decisions. Product-keyed Kafka preserves partition order. PostgreSQL row locks, receipts and transactional pricing audits keep inventory deterministic under replay. Redis supports delivery/fallback, while a bounded socket queue prevents a slow browser from blocking others.

**Second minute — the separate advisory path.** One independent forecast process observes the inventory topic using a different group. It confirms a durable core receipt before counting completed sales and writes event-time sales buckets with its own deduplication receipt. It can lag or stop without becoming an inventory dependency. Its snapshot histories and observer freshness are explicit.

**Third minute — forecasting and evidence.** A seeded simulator creates four days of structured, stock-constrained data. Causal lag/rolling features feed a moving-average baseline and histogram gradient boosting. Chronological splits purge overlapping target horizons at boundaries. On 5,256 test examples, measured MAE was 17.20 versus 6.13 units; these are synthetic outcomes. A validation residual band achieved 89.65% test coverage without a future coverage guarantee. Numerical JSON trees permit safe runtime inference without pickle.

**Fourth minute — decisions and explanations.** Deterministic thresholds classify stockout risk, with a constant-rate time estimate. Replenishment uses the upper band plus safety stock minus available stock, bounded by configuration. Recommendations are stored, approved/rejected by protected local controls, and executed by a durable Kafka outbox with stable event IDs. The analyst has only bounded read tools. The chosen evidence-only mode formats their verified facts directly; an optional provider adapter is tested with mocks, not a live external provider.

**Fifth minute — UI, failures and limits.** Operations answers what needs attention; details separate observations from predictions. The existing rAF/Zustand/memoized rendering remains on Engineering. Model failure falls back to a labelled baseline; worker failure makes predictions stale; inventory still processes. Separate integration, ML and benchmark workflows avoid heavy normal CI. Local tests do not prove production capacity. Real data, authentication, retention, multi-gateway fanout and richer model monitoring are future deployment work.

## Twenty implementation-specific questions

1. **Why Kafka?** It provides partitioned, replayable events and independent inventory/feature consumer groups. Redis Pub/Sub alone would not retain missed inventory events for recovery.
2. **Why product ID as the key?** Changes for a product share one partition order. Global ordering and cross-topic ordering are not promised.
3. **How are duplicates harmless?** Core receipts commit with inventory effects. The feature observer has its own receipt transaction, and approved/scenario events reuse stable IDs on publication retries.
4. **Why allow operator commands without inventory versions?** The trusted command specifies a quantity; under the core row lock the next revision is computed from durable state. Existing simulator snapshot events still require an exact version and snapshot checks. Kafka access remains a trust boundary.
5. **What does PostgreSQL own?** Inventory, core/feature receipts, pricing audits, sales buckets, forecasts, scenario plans and operator decisions. Redis is a cache/telemetry layer.
6. **What caused the old event lag?** Measured serial per-event database work and repeated publication/commit overhead. Transactional batches and grouped commits improved the measured socket tail; browser FPS alone could not reveal backlog.
7. **Can forecasting stop inventory?** It has its own process/group and never runs in the core handler. Shared database/Kafka resources can still create contention, so isolation must also be measured.
8. **How are invalid events treated by the observer?** It does not count missing/nonprocessed receipts as sales. It waits while the core has not advanced; when the core offset passes a missing receipt, that record can be skipped as invalid/dead-lettered.
9. **Why sales instead of latent demand?** Completed sales are an observable operational target. Simulated latent attempts are retained separately; an empty shelf censors sales and cannot prove demand disappeared.
10. **What exactly is predicted?** Twelve five-simulated-minute bins of completed sales. Offline origins occur at bucket boundaries; live targets begin at the next whole bucket, with the alignment/acquisition gap documented.
11. **What prevents leakage?** Features use earlier completed sales and known state. All products use chronological cutoffs; target-window purge gaps separate train/validation/test. No future attempt counts or future scenario labels become features.
12. **Why a baseline?** It establishes whether ML improves on a simple recent-sales estimate. Here the last-three-bin mean × twelve had worse held-out MAE/RMSE; the comparison is specific to synthetic data.
13. **Why histogram gradient boosting?** It fits numerical tabular lag features without a neural architecture. The trained artifact has 100 small trees and can be exported to bounded numerical JSON.
14. **Are prediction ranges guaranteed?** No. A validation residual quantile calibrates a band with measured test coverage. Correlated horizons and regime changes prevent a general coverage guarantee. Baseline fallback bands are explicitly heuristic.
15. **How is stockout risk calculated?** Critical means no available stock or constant-rate estimated depletion within fifteen simulated minutes. High means expected horizon sales cover available stock; medium means only the upper band does; otherwise healthy. It is a policy class, not a calibrated probability.
16. **How is replenishment calculated?** For nonhealthy risk: ceil(upper forecast + configured safety stock − available stock), clamped to zero and configured maximum. Forecast uncertainty is not an optimized supplier lead-time policy.
17. **How does approval survive a crash?** Approval stores status and a stable event ID first. A worker publishes and marks acknowledgement; a crash between these can publish twice, but the core receipt prevents double stock effects. EXECUTED requires a processed receipt.
18. **What does rAF batching preserve?** Network ingestion is independent of rendering. Latest per-product updates coalesce each frame, normalized Zustand selectors retain unrelated identities, and memoized cards limit rendering. Engineering still exposes all four comparison modes.
19. **What happens during a slow client or catalog failure?** Bounded queues disconnect slow clients; reconnect fetches a snapshot. The catalog circuit can OPEN, serve validated stale Redis data and later probe HALF_OPEN. Retail controls refuse stale recommendations; stale forecast data is displayed explicitly.
20. **How is the analyst grounded and read-only?** Typed bounded tools read products, forecasts, actual pricing decisions, scenarios, recommendations and system/model health. There is no write tool or unrestricted SQL. Evidence-only responses format retrieved values/timestamps directly. Optional provider calls have timeouts/call limits and numerical validation, but full prose faithfulness would need further evaluation before public use.
21. **How are deployed forecasts monitored?** Independent feature lag/watermark, model version, successes/failures, fallback count, last forecast latency/time, recommendation statuses and recent matured MAE/RMSE. Mixed-regime online errors are separate from held-out scores.
22. **What would change for production?** Real authenticated operators, broker/database least privilege, actual demand/supply data, retention and restore, interval/drift validation, model rollout/version policies, group-wide monitoring, gateway fanout and TLS load balancing. The current deployment is local and single advisory-worker.
